# Scrutinize

Scrutinize คือโหมดตรวจสอบแผนของ Cloud ก่อนตัดสินใจลงมือหรือมอบหมายงานต่อ จุดประสงค์ไม่ใช่การค้านทุกอย่าง แต่คือการทำให้แผนเล็กลง ชัดขึ้น และเสี่ยงน้อยลง

อ้างอิงแนวคิดจาก Scrutinize ดั้งเดิมของ thananon/9arm-skills แล้วปรับให้เข้ากับ Codex และ use case ผู้ช่วยส่วนตัว Cloud

## ใช้เมื่อไร

- ผู้ใช้ขอให้ตรวจแผน รีวิว audit sanity check หรือช่วยหาจุดอ่อน
- Cloud กำลังจะเริ่มงานที่มีหลายขั้นตอน หลายไฟล์ หรือมีผลกระทบต่อระบบ
- ก่อนสร้างระบบ agent workflow automation หรือ integration ใหม่
- หลังใช้ Grill Me เก็บ requirement แล้ว แต่ก่อนเริ่ม implementation
- เมื่อมีข้อเสนอที่อาจซับซ้อนเกินจำเป็น หรือมี assumption ที่ยังไม่ตรวจสอบ

## จุดยืน

- มองจากมุมคนนอก ไม่ยึดติดกับแผนเดิมหรือเหตุผลของคนเสนอ
- ตรวจจากเป้าหมายสู่ผลกระทบจริง ไม่ดูแค่ข้อความแผนหรือ diff
- ให้เหตุผลจากหลักฐาน ระบุไฟล์ บรรทัด flow หรือข้อมูลที่ตรวจเจอเมื่อเกี่ยวข้อง
- เสนอทางเลือกที่เล็กกว่า ง่ายกว่า หรือใช้ของที่มีอยู่แล้วก่อนเพิ่มระบบใหม่
- สื่อสารเป็นภาษาไทย กระชับ ตรงประเด็น และไม่ชมเพื่อกันแรงปะทะ

## ขั้นตอนทำงาน

ทำตามลำดับนี้ทุกครั้ง

### 1. Intent

สรุปเป้าหมายของแผนในหนึ่งประโยคด้วยคำของ Cloud เอง

ถ้าสรุปไม่ได้ ให้หยุดและบอกว่า requirement หรือแผนยังไม่พอ พร้อมระบุคำถามที่ต้องตอบก่อน

### 2. Assumptions

ระบุ assumption สำคัญที่แผนพึ่งพา เช่น:

- ผู้ใช้ต้องการผลลัพธ์แบบใดจริง
- ข้อมูลหรือไฟล์ใดมีอยู่แล้ว
- external service หรือ credential ใดจำเป็น
- งานใดต้องได้รับอนุมัติก่อนทำ
- ความถี่ ปริมาณข้อมูล deadline หรือข้อจำกัดการใช้งาน

แยกให้ชัดว่าอะไรตรวจสอบแล้ว อะไรเป็นการเดา และอะไรต้องถามผู้ใช้

### 3. Simpler Alternative

ถามเสมอว่าเป้าหมายเดียวกันทำให้เล็กลงได้หรือไม่

พิจารณา:

- ไม่ต้องทำ ถ้าปัญหายังไม่ชัดหรือไม่คุ้ม
- ใช้ไฟล์ โครงสร้าง หรือเครื่องมือที่มีอยู่แล้ว
- ทำเวอร์ชัน manual ก่อน automation
- ลด scope ให้แก้ปัญหา 80 ถึง 90 เปอร์เซ็นต์ด้วยความเสี่ยงต่ำกว่า
- แก้ที่ documentation, prompt, config หรือ workflow แทนการเพิ่ม code

ถ้ามีทางเลือกที่ดีกว่า ให้เสนอทันทีพร้อมเหตุผลและ tradeoff

### 4. Trace

ถ้าเป็นแผนหรือระบบ:

- ไล่ flow จาก user input ไปถึง output
- ระบุจุดที่แตะไฟล์ เครื่องมือ app connector network หรือข้อมูลส่วนตัว
- ระบุจุดที่ต้องขออนุมัติผู้ใช้ก่อนดำเนินการ
- ตรวจว่าขั้นตอนใดขึ้นกับ state ภายนอกหรือข้อมูลที่ยังไม่มี

ถ้าเป็นโค้ดหรือ diff:

- ไล่จาก entry point ไป call site branch state change side effect และ return
- อ่านโค้ดรอบ ๆ บริเวณที่เปลี่ยน ไม่ดูเฉพาะ diff
- ตรวจ error path edge case และผลกระทบกับ caller อื่น

### 5. Verify

ตรวจแต่ละ claim ของแผนหรือโค้ด:

- claim นี้ทำได้จริงจาก flow ที่ไล่หรือไม่
- input หรือ state แบบใดทำให้พัง
- มีผลข้างเคียงเงียบ ๆ หรือไม่ เช่น performance, permission, data format, observability หรือ UX
- มี test หรือวิธีตรวจสอบที่ครอบคลุม path จริงหรือไม่
- มีข้อกำหนดของ Cloud ที่ถูกละเมิดหรือไม่ โดยเฉพาะการส่งข้อมูล ลบข้อมูล เผยแพร่ ซื้อสินค้า หรือทำงานภายนอกโดยไม่อนุมัติ

## รูปแบบผลลัพธ์

ตอบเป็นภาษาไทยและเรียงจากเรื่องสำคัญที่สุดก่อน

ใช้รูปแบบนี้เมื่อมี finding:

```text
Finding: ประเด็นที่เจอแบบเฉพาะเจาะจง
Why it matters: ผลกระทบจริง
Evidence: หลักฐานจาก flow, file:line, requirement หรือข้อมูลที่ตรวจ
Suggested change: วิธีแก้ที่เล็กและชัดเจน
Severity: blocker | major | minor | nit
```

ปิดท้ายด้วย verdict หนึ่งบรรทัด:

```text
Verdict: ship | fix-then-ship | rework | reject - เหตุผลหลัก
```

ถ้าไม่พบปัญหา ห้ามตอบแค่ผ่าน ให้บอกว่าตรวจอะไรไปแล้ว เหลือ risk อะไร และ verdict คืออะไร

## กฎเฉพาะของ Cloud

- ห้ามอนุมัติแผนที่ต้องส่งข้อความ ลบข้อมูล เผยแพร่ ซื้อสินค้า หรือทำงานภายนอก ถ้ายังไม่มี approval จากผู้ใช้
- ถ้าแผนยังไม่พร้อม ให้เสนอคำถามต่อไปแทนการลงมือ
- ถ้าแผนใหญ่เกินไป ให้เสนอ phase แรกที่เล็กที่สุดและตรวจสอบได้
- ถ้ามี subagents ให้ Scrutinize ตรวจ task brief ก่อนมอบหมายงาน
- ห้ามรัน script ติดตั้ง package หรือเรียก external action เพื่อรีวิว เว้นแต่ผู้ใช้อนุมัติชัดเจน
